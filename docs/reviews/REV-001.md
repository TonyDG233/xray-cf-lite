### P1（严重，应修）

**P1-1 自定义快捷命令 URL 未转义，导致 root 命令注入**
- 位置：`xray_cf_lite.sh:1515-1524`（`write_shortcut_remote` 的 heredoc 直接展开 `${url}`）、`xray_cf_lite.sh:1743-1750`（自定义 URL 仅校验 `^https?://[^[:space:]]+$`）、调用点 `xray_cf_lite.sh:1727-1755`（菜单 9 → 5 → 3）
- 问题：该正则只禁止空白，允许 `$`、`(`、`)`、`;`、反引号、引号等 shell 元字符。写入 `/usr/local/bin/x` 的内容也未加引号。实测输入 `https://example.com/$(id)` 被接受，生成的快捷命令为：
  ```sh
  exec bash <(curl -fsSL https://example.com/$(id)) "$@"
  ```
  用户以 root 运行 `x` 时，`$(id)` 会以 root 执行。属于用户输入触发的本地提权/命令注入（需用户粘贴恶意 URL，但该功能本身就鼓励粘贴"自定义 Raw URL"）。
- 建议修法：不要把 URL 直接拼进 shell 脚本。至少使用 `printf '%q'` 转义后再写入；或收紧校验，拒绝 `$ \` " ' ( ) ; | & < >` 等字符（只保留 `[A-Za-z0-9:/._~%?&=+@!-]`）。`ensure_shortcut`（`xray_cf_lite.sh:1767-1786`）同样存在未加引号的 `${SCRIPT_RAW_URL}`，建议一并加固（纵深防御）。
- 备注：若项目安全基线把"任意 root 代码执行"视为阻断，可将本条提升为 P0。

**P1-2 新增 `BASH_SOURCE` 守卫 + `set -u` 破坏 `bash -s < file` / `curl | bash`**
- 位置：`xray_cf_lite.sh:1837-1839`（`[[ "${BASH_SOURCE[0]}" == "${0}" ]]`）、`xray_cf_lite.sh:2`（`set -euo pipefail`）
- 问题：当 bash 从 stdin 读取脚本（`bash -s < xray_cf_lite.sh`、`curl ... | bash`）时，`BASH_SOURCE` 为空数组，`${BASH_SOURCE[0]}` 在 `set -u` 下直接报 `unbound variable` 并退出，菜单根本不会出现。实测：
  ```
  === bash <(cat xray_cf_lite.sh) ===  -> rc=1, "请使用 root 运行此脚本"（守卫通过，main 已进入）
  === bash -s < xray_cf_lite.sh ===    -> rc=1, "bash: line 1837: BASH_SOURCE[0]: unbound variable"
  ```
  注意：README 文档化的 `bash <(curl ...)` 与快捷命令 `x` 都用进程替换，**不受影响**；但 `| bash` 是极常见的替代安装方式，属于本次改动引入的回归（HEAD 此处是无条件 `main "$@"`）。
- 建议修法：改为 `if [[ "${BASH_SOURCE[0]:-$0}" == "$0" ]]; then main "$@"; fi`。这样 `bash script.sh`、`bash <(...)`、`bash -s < ...` 都会进入 main，而 `source` 时 `$0` 与 `BASH_SOURCE[0]` 不同，不会误跑。

**P1-3 Worker SSRF 防护可被"公网 DNS 解析到私网"和"重定向"绕过**
- 位置：`cf_sub_worker.js:308-334`（`isSafeSourceUrl` 只检查字面 hostname）、`cf_sub_worker.js:365-375`（`fetch` 使用 `redirect: "follow"`）
- 问题：`?ip_urls=` 只做 hostname 字符串判断，不做 DNS 解析；且拉取时自动跟随重定向。实测以下 URL 被接受并进入 fetch 列表：
  ```
  ACCEPTED public DNS -> 127.0.0.1   http://localtest.me/        -> fetched=["http://localtest.me/"]
  ACCEPTED nip.io -> 127.0.0.1       http://127.0.0.1.nip.io/    -> fetched=["http://127.0.0.1.nip.io/"]
  ACCEPTED localtest.me. (trailing)  http://localtest.me./       -> fetched=["http://localtest.me./"]
  ```
  字面私网 IP（`127.0.0.1`、`10.0.0.1`、`192.168.1.1`、`169.254.169.254`、`[::1]`、`0.0.0.0`）以及整数/十六进制/IPv4-mapped 形式均被正确拦截（C4 指定用例全 PASS）。但"公网域名解析到 127.0.0.1"和"302 跳转到私网"仍可绕过；`redirect: "follow"` 使初始 URL 校验形同虚设。
- 建议修法：至少改为 `redirect: "manual"` 并逐跳校验 `Location` 后再请求；Workers 默认没有 DNS 解析 API，最稳妥的是把 `?ip_urls=` 限制为可配置的域名 allowlist（或干脆移除该查询参数，只信任 `env.IP_URLS`），并显式拒绝已知回环别名（`localtest.me`、`*.<ip>.nip.io`、`sslip.io` 等）；补 6to4/Teredo/NAT64 前缀判断（`cf_sub_worker.js:280-290` 目前未覆盖）。
- 备注：Cloudflare 平台可能额外阻断私网出站，实际可利用性低于传统服务器；但代码声称的 SSRF 防护确实不完整。

### P2（改进建议）

**P2-1 Worker 把非法 IPv4 当域名接受，生成脚本不会生成的坏节点**
- 位置：`cf_sub_worker.js:154-160`（`isDomainName` 未要求含字母）、`cf_sub_worker.js:222-226`、`cf_sub_worker.js:426-429`；对照脚本 `xray_cf_lite.sh:676-692`（逐段 <=255 且域名分支要求含字母）
- 问题：`999.999.999.999`、`1.2.3.999` 不是合法 IPv4，但 `isIPv4` 失败后 `isDomainName` 因其只含数字和点而返回 true。实测 Worker 会输出：
  ```
  INVALID_IP_EMITTED=true (good present=true)
  DOMAIN 999.999.999.999 status=200 firstNode=vless://...@999.999.999.999:443?...
  ```
  脚本的 `fetch_and_clean_preferred_ips` 会正确过滤。该差异使 Worker 订阅混入连不上的坏节点，且与 Worker 头部注释"按脚本规则清洗"的声明不符。
- 建议修法：在 `isDomainName` 中要求至少一个字母（`if (!/[a-zA-Z]/.test(host)) return false;`），或在 `parsePreferredEndpoint` 中先拒绝 `/^[0-9.]+$/` 的主机。

**P2-2 未使用的变量（死代码）**
- 位置：`xray_cf_lite.sh:21`（`SUB_BASE`，全文仅此一处赋值，`build_link` 已改用局部 `sub_base`）、`xray_cf_lite.sh:32`（`PROTO_FLAG`，未被任何函数引用）
- 建议：删除或实际使用，避免后续维护误判。

**P2-3 卸载未清理本地离线脚本**
- 位置：`xray_cf_lite.sh:12`（`LOCAL_SCRIPT_PATH`）、`xray_cf_lite.sh:1186-1189`（`do_uninstall` 只删 `state.json`、快照、CF 凭据、`local_sub/`）
- 问题：菜单 9 → 5 → 2 生成的 `/etc/xray-cf-lite/xray_cf_lite.sh` 在卸载后残留；README 的"清理本地状态/凭据/订阅快照"未提及该文件。
- 建议：`rm -f "$LOCAL_SCRIPT_PATH"`；如目录为空可一并 `rmdir`。

**P2-4 Worker 拉取源无响应体大小上限**
- 位置：`cf_sub_worker.js:365-383`
- 问题：`response.text()` 无长度限制，恶意/异常源可返回超大响应，消耗 Worker 内存/CPU（最终被顶层 catch 吞成空订阅）。
- 建议：检查 `Content-Length` 或按流读取并在阈值（如 2 MiB）处中止。

**P2-5 `ev=et=mess=no` 返回空订阅 200**
- 位置：`cf_sub_worker.js:628-640`、`cf_sub_worker.js:697-706`
- 行为：三个协议都显式 `no` 时，`protocolOrder` 为空，`plainText=""`，返回 `200` + 空体（Base64 空串）。不是错误，但对客户端表现为"订阅为空"。
- 建议：可返回 `400 no protocol enabled` 以更明确；若为兼容旧客户端保持 200，请在 README 注明。

**P2-6 脚本本地优选源无 SSRF/scheme 保护（低风险）**
- 位置：`xray_cf_lite.sh:715`（直接 `curl` 用户配置的 URL）、`xray_cf_lite.sh:1607`（添加源只校验 `https?://`）
- 说明：脚本以 root 运行在用户自己的 VPS 上，源由用户自己添加，风险远低于 Worker；但若 `state.json` 被他人篡改，可让 VPS 去请求云元数据地址。属加固建议，非阻断。
- 建议：可选地拒绝私网/环回/链路本地目标（与 Worker 的 `isPrivateIPv4/6` 同口径）。

**P2-7 `do_show_config` 对缺失 `.links` 不健壮**
- 位置：`xray_cf_lite.sh:1363`（`print_links "$(echo "$state" | jq '.links')"`，未用 `// {}`）
- 问题：若旧/手工 state 缺少 `links`，`jq '.links'` 得到 `null`，`print_links` 内 `to_entries` 失败，`set -e` 下可能让 `do_show_config` 非零退出。当前旧版 state 一定含 `links`，故仅属健壮性建议。
- 建议：改为 `jq '.links // {}'`。

## 5. 特别结论

**问题**：用户在已有纽约 VPS 上执行

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/TonyDG233/xray-cf-lite/main/xray_cf_lite.sh)
```

后，能否在**不重新输入 CF Global API Key、不卸载重装、不重启 xray** 的前提下，进入菜单 9 直接获得自定义优选节点与订阅？

**结论：YES（可以），但有两个使用前提。**

依据（均为实际代码路径/实测）：

1. **入口方式可用**：`main` 守卫对进程替换 `bash <(file)` 成立（实测 `bash <(cat xray_cf_lite.sh)` 进入 main）；README 与快捷命令 `x` 都用该方式。`main` 首先 `ensure_shortcut`（仅当旧 `/usr/local/bin/x` 含 `byJoey/xray-cf-lite` 时迁移，否则原样保留）→ `load_state` → 打印菜单，**不调用 `prompt_cf`、不调用 CF API、不重启 xray**（`xray_cf_lite.sh:1788-1834`）。
2. **旧 state 兼容**：HEAD 版本 `do_install` 已写入 `domain/uuid/routes/dns_backup/ssl_backup/origin_rules_backup/security_backup/links`（`git show HEAD:xray_cf_lite.sh:786-794`）；新脚本的 `state_get_*` 对缺失的 `sub_base/sub_token/port_mode/ip_urls` 返回正确默认值（B2 实测）。菜单 9 → 1 只需 `domain/uuid/routes`，不依赖 CF 凭据。
3. **菜单 9 → 1 直接出本地订阅**：`generate_local_subscriptions` 读取 `state.json`，拉取 4 个优选源，生成 `nodes_all.txt`、`sub_all_base64.txt` 等（`xray_cf_lite.sh:793-912`）。全程无 `cf_call`/`load_cf_account`（B8 静态 grep + 运行时 tripwire 双证），**不重启 xray**、不写 xray 配置。
4. **端到端实测**：用旧 state（无新字段）模拟 `9 → 4`（设置 `https://sub.example.com` + `mytoken`）→ `9 → 1`（生成本地订阅）→ `0`，结果：`sub_base/sub_token` 正确写入、`links` 带 `token=mytoken`、本地节点文件生成（17 条）、四类备份字段原样保留、`cf.log` 为空（B9b `run2_*` 全 PASS）。
5. **前提 A（网络）**：优选节点来自 4 个外部源（`xray_cf_lite.sh:23-28`）。若 VPS 无法访问这些源，`fetch_and_clean_preferred_ips` 会逐源告警并跳过（`xray_cf_lite.sh:715-717`），但**仍会生成仅含自身域名（443）的原生节点**，不会整体失败。因此"获得订阅"始终成立，"获得优选 IP 节点"取决于源可达性。
6. **前提 B（远程订阅 URL）**：`DEFAULT_SUB_BASE` 仍是已失效的 `https://yx-auto.pages.dev`（`xray_cf_lite.sh:20`）。若用户要的是**在线远程订阅**（而非本地 Base64 文件），需在菜单 9 → 4 填入自建 Worker 地址（例如 `https://sub.example.com`，可带 `token`）。这一步同样不需要 CF Key、不重装、不重启 xray，且实测生成 `https://sub.example.com/<uuid>/sub?...&token=...`，与 `cf_sub_worker.js:589` 路由契约匹配。

因此：**"菜单 9 直接获得自定义优选节点与本地订阅" = YES；"直接获得可用的在线远程订阅" = 需先做一次 9 → 4 设置 Worker 地址（仍满足免 CF Key/免重装/免重启）**。README 第 75-118 行的描述与实测行为一致。

## 6. 测试环境与限制（诚实记录）

- 宿主为 Windows 10 + Git Bash（MSYS bash 5.2.37），**非 Linux**；未使用 WSL（无发行版）。
- Git Bash 未自带 `jq`，为执行脚本沙盒，仅将 `jq-1.7.1` 静态二进制下载到 `%TEMP%\kilo\revtools`（未安装到系统 PATH/系统目录），测试后随沙盒清理。
- 未访问真实 4 个优选源；B4/B5/B6/A3 使用本地 `python -m http.server`（127.0.0.1:8791）+ 构造的 `mix.txt`/`ports.txt` mock，覆盖 CRLF、无末尾换行、广告/横幅、CSV、重复、非法 IP、IPv6、非 TLS 端口、404、拒连。
- 未发起任何 Cloudflare API 请求：所有 CF 相关函数在沙盒中被替换为 tripwire/空实现。
- 未执行 `do_install`/`do_uninstall` 等会改写 `/etc`、`/usr/local` 的分支；所有状态路径经 `XRAY_CF_LITE_STATE_DIR`/`XRAY_CF_LITE_LAST_LINKS_PATH`/`XRAY_CF_LITE_SHORTCUT_PATH`/`XRAY_CF_LITE_RAW_URL` 指向 `%TEMP%`。

- MSYS/NTFS 无法呈现 POSIX `600`（直接 `chmod 600` 后 `stat` 仍为 644）；B6 权限项按"代码路径正确 + 环境无法呈现"记录。

- `jq` 路径参数受 MSYS 自动路径转换影响（`/11111111-vl` 被转成 `D:/coding/Git/...`）；测试中通过 `MSYS2_ARG_CONV_EXCL` 关闭转换后复测，确认为环境行为而非脚本缺陷。
