## 决策点

- 决策点 1：`?ip_urls=` 重新开放后，任何持有 TOKEN 的人都能让 Worker 去抓任意 https 地址（部分 SSRF 面重新打开）
- 现状：鉴权通过后才解析，仅接受 `https://` 前缀 + `isSafeSourceUrl`（拒绝私网/环回/链路本地/单标签主机名/回环别名后缀），去重后最多 32 条，单源 2 MiB、8s 超时、最多 3 跳重定向且每跳复检（cf_sub_worker.js:716–721、:349–383、:468–502）。没有“按部署配置固定源”的开关，也没有对 `ip_urls` 的签名校验；而该参数会被脚本写进分享给客户端的订阅链接。
- 对用户的影响：拿到 TOKEN 或拿到订阅链接的人可让 Worker 代抓任意公网 https 地址（可用于探测/放大请求、消耗 Worker 额度）；因为 Cloudflare 侧通常拦截内网目标，真正打到内网的概率低，但“抓取源由客户端决定”这一信任模型变化对多用户共享的 Worker 有实际风险。
- 我的建议：采纳（本轮需求明确要恢复透传），但加一层部署方可控的开关：例如 `env.ALLOW_QUERY_SOURCES` 默认关闭、或对 `ip_urls` 做 HMAC 签名（脚本与 Worker 共享密钥），并在 README 提醒“订阅链接等同于源配置权限，不要公开分享”。

- 决策点 2：VPS 直连订阅默认端口 18080，需要该端口对公网可达
- 现状：`local_sub_server.py:129` 默认 18080，`:137` 绑定 `0.0.0.0`，README.md:96 直接给出 `http://服务器IP:18080/<密钥>/sub`；示例 unit 未涉及防火墙/安全组，服务为明文 HTTP。
- 对用户的影响：VPS 在 NAT 后或云安全组未放行 18080 时，客户端只会“连不上”，且没有错误提示；明文 HTTP 下订阅路径里的密钥可被链路中间人截获，拿到密钥即可读取全部节点配置。部分运营商/网络还会拦截非常用端口。
- 我的建议：采纳默认端口（保持开箱即用），但在 README/示例中补两点：①云厂商安全组与 `ufw/firewalld` 需放行 18080，或改用 443 反代；②对外暴露时建议走 Caddy/Nginx 的 HTTPS 反代并限制来源 IP，至少不要长期裸跑明文。

- 决策点 3：state 里没有 `sub_token` 时，Python 服务一律返回 403，用户必须自己设置密钥
- 现状：`local_sub_server.py:98–100`，`state.sub_token` 为空且未传 `--token`/`LOCAL_SUB_TOKEN` 时直接 403，并回一句“未设置订阅密钥: 请运行 x 进入 9 -> 4 设置…”。
- 对用户的影响：老用户或跳过菜单 9→4 的用户会看到 403，容易误判为服务没起来；好处是不会出现“无鉴权公网订阅”这种更糟的默认。另需注意 `ensure_state_sub_fields` 会把缺省 `sub_token` 固化为空串，所以“未设置”是常见初始态，不是异常。
- 我的建议：采纳（安全默认正确），但把“必须先设密钥”写进 README 的启动步骤，并在 systemd 示例里给出 `Environment=LOCAL_SUB_TOKEN=<自定密钥>` 的注释行，避免用户只看到 403 而无从下手。
